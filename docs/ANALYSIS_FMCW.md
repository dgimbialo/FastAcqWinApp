# FastAcqWinApp — аналіз коду, функціональності та пропозиції змін

**Фокус:** обробка сигналу биття (IF/beat) FMCW-радара, якість вимірювання частоти биття, відображення, редизайн UI.
**Дата аналізу:** 2026-10-05. **Обсяг коду:** 38 файлів, ≈4 540 рядків C++17/MFC.

> Посилання виду `Файл.cpp:NN` вказують на рядок у `FastAcq/`.

---

## 0. Коротко (TL;DR)

1. **Архітектура здорова**: окремий потік COM-порту → потоковий парсер із CRC → кільцевий буфер кадрів → UI через `PostMessage`. Це правильний каркас, його варто зберегти.
2. **Критична вада DSP**: локальна FFT бере лише **перші `fftSize` відліків** кадру (`LocalFft.cpp:66-68`), тобто за замовчуванням 16 384 із 131 072 — **12,5 % кадру, 25 % UP-рампи**. Для FMCW це означає втрату ~75 % ефективної смуги, тобто **роздільна здатність по дальності гірша в 4 рази**, ніж дозволяє пристрій.
3. **Панелі «Spectrum UP» і «Spectrum DOWN» показують один і той самий спектр** (`Tab1Wnd.cpp:344-349`): обидві отримують FFT усього кадру. На скріншоті 1 це видно (однакові таблиці піків). Частота биття UP/DOWN окремо рахується лише для підпису у Waveform-вкладці і ніде не використовується для дальності/швидкості.
4. **Видимий баг індексації кільцевого буфера**: `ChirpStore::Push` повертає позицію в `deque`, яка після заповнення (200 кадрів) завжди = 199 і зсувається при кожному `pop_front`. У списку кадрів з'являються **дублікати та пропуски** (скріншот 1: `761, 761, 763, 763 …`), вибір старого кадру зі списку показує не той кадр, «Save Frame» зберігає не той кадр.
5. **Немає жодної «радарної» величини**: спектр лише в Гц, без осі дальності (м), без швидкості, без SNR, без параметрів радара (f₀, B, T_ramp). Застосунок сьогодні — це осцилограф + аналізатор спектра, а не аналізатор FMCW.
6. **Шкала спектра/водоспаду «дихає»**: нормування відносно `m_maxSeen` із розпадом 0.9 за кадр, водоспад — лінійний, не в дБ. Слабкі цілі (на −40…−60 дБ від найсильнішої) у водоспаді невидимі.
7. **Уся DSP виконується в UI-потоці** (3 FFT на кадр + 3–4 копії масиву до 1,3 МБ), повідомлення про кадри не об'єднуються — при збільшенні швидкості потоку інтерфейс почне «відставати».
8. **Вузьке місце — USB FS CDC**: за скріншотом кадри приходять кожні ~453 мс при інтервалі 100 мс; 262 КБ RAW + FFT ≈ 0,65 МБ/с — це стеля Full-Speed CDC. Жодна PC-оптимізація не підніме FPS без змін у прошивці (12-бітне пакування, децимація на MCU, USB HS).
9. **UI функціональний, але «сирий»**: немає курсорів/маркерів, осі часу на осцилограмі, осей і колірної шкали водоспаду, режиму Hold/Live, збереження налаштувань, запису/відтворення, DPI-awareness. Мертвий код `Theme.h/ModernButton/ModernTabCtrl` свідчить про незавершену спробу редизайну.
10. Рекомендована стратегія: **(а)** виправити P0-дефекти, **(б)** винести DSP у окремий модуль/потік і побудувати повноцінний FMCW-конвеєр (повна рампа → детренд → вікно → zero-pad → real-FFT → дБ → шум/CFAR → інтерполяція піка → R, v з UP/DOWN), **(в)** перебудувати головний екран навколо «range profile + водоспад + таблиця цілей», **(г)** додати запис/відтворення, що одночасно дасть тести без заліза.

## 1. Що є зараз

### 1.1. Потік даних

```
COM (USB CDC) ──ReadFile 4 КБ──▶ SerialWorker::ThreadLoop ──▶ ProtocolParser::Feed
                                                              │ (magic → header → raw → fft → CRC32)
                                                              ▼
                         ChirpStore (deque, 200 кадрів) ◀── callback (move)
                                  │ PostMessage(WM_APP_FRAME_READY, idx)
                                  ▼
          CMainFrame::OnFrameReady ─ GetAt(idx) (копія кадру) ─▶ ShowFrameAt
                 ├─ Tab1Wnd::ShowFrame  → 2× LocalFft::Compute (UP, DOWN) → WaveformView ×2
                 └─ Tab2Wnd::ShowFrame  → 1× LocalFft::Compute (весь кадр) → SpectrumView ×2 + WaterfallView
```

### 1.2. Модулі

| Модуль | Призначення | Оцінка |
|---|---|---|

| `ProtocolParser` | автомат збирання кадрів з байтового потоку | Добре; є дрібні вади (див. §2) |

| `ChirpStore` | кільце кадрів із критичною секцією | Баг індексації; копіювання при `GetAt` |
| `LocalFft` | radix-2 FFT, 4 вікна, параболічна інтерполяція піка | Працює, але використовує лише початок кадру |

### 1.3. Сильні сторони, які варто зберегти

- Нульові залежності, один `.exe`, швидкий старт — реальна перевага для лабораторного інструмента.
- Чистий потоковий парсер із ресинхронізацією за magic і CRC32 на весь кадр.
- Правильне розділення потоків (COM-потік не торкається UI, тільки `PostMessage`).
- Min/max-децимація в осцилограмі — правильний спосіб малювати 131 k точок без аліасингу.
- Службові кадри (PONG/STATUS/ACK) вже відокремлені від даних.

## 3. Обробка сигналу биття FMCW: аналіз і рекомендований конвеєр

### 3.1. Параметри системи (з коду та плану)

| Параметр | Значення | Джерело |
|---|---|---|
| Fs (АЦП, AD9226) | 60,0586 МС/с | `MainFrame.h:98` |
| Частота модуляції (трикутник, DAC) | 100…24 000 Гц, типово 458 Гц | `SettingsTab.cpp:146-148` |
| Період модуляції при 458 Гц | 2,183 мс ≈ 131 072 відліки | `IMPLEMENTATION_PLAN.md` («applied=131072») |
| Тривалість однієї рампи T_ramp | 1,092 мс ≈ 65 536 відліків | половина періоду |
| FFT за замовчуванням | 16 384 (0,273 мс) | `LocalFft.h:13` |
| Максимум відліків у кадрі | 650 000 (10,8 мс) | `SettingsTab.cpp:151` |

### 3.2. Базові формули (трикутна модуляція)

- Частота биття від дальності: **f_R = 2·B·R / (c·T_ramp)**; дальність: **R = c·T_ramp·f_b / (2·B)**.
- Доплер: **f_D = 2·v / λ = 2·v·f₀ / c**.
- UP/DOWN рампи: f_up = f_R − f_D, f_down = f_R + f_D (ціль наближається) ⇒
  **R = c·T_ramp·(f_up + f_down) / (4·B)**, **v = λ·(f_down − f_up) / 4**.
- Роздільна здатність по частоті при спостереженні T_obs: Δf = 1/T_obs ⇒ **ΔR = c / (2·B_eff)**, де B_eff = B·(T_obs/T_ramp). Zero-padding і більший розмір FFT **не** покращують ΔR, лише інтерполюють спектр.
- Максимальна однозначна дальність: R_max = c·T_ramp·(Fs_eff/2) / (2·B).
- Роздільна здатність по швидкості (burst із M чірпів, період повторення T_PRI): Δv = λ / (2·M·T_PRI); однозначна швидкість ±λ/(4·T_PRI).

**Числовий приклад** (24 ГГц, B = 200 МГц, T_ramp = 1,092 мс, Fs = 60 МС/с):

| Величина | Поточний код (16 384 відл.) | Повна рампа (65 536 відл.) |
|---|---|---|
| T_obs | 0,273 мс | 1,092 мс |
| Δf (бін) | 3 666 Гц | 916 Гц |
| B_eff | 50 МГц | 200 МГц |
| **ΔR** | **3,0 м** | **0,75 м** |
| f_b на 1 м | 1 223 Гц/м | 1 223 Гц/м |
| f_b на 100 м | 122 кГц | 122 кГц |

Висновок: частота биття для реалістичних дальностей — **десятки–сотні кГц**, а Fs = 60 МГц дає надлишкову дискретизацію в ~250 разів. Корисно використати це: або довга FFT (65 536 точок — ~3–5 мс на ПК з real-FFT), або **децимація ×32…×256** з антиаліасним FIR, після якої FFT на 1–4 k точок дає ту саму Δf = 1/T_ramp, але в 50 разів дешевше, і залишає запас на zero-padding ×4–8 та усереднення.

### 3.3. Проблеми поточного конвеєра

1. Використовується лише початок кадру (§2 #2) — втрата роздільної здатності в 4 рази.
2. UP і DOWN не обробляються як окремі рампи у спектральній вкладці (§2 #3); f_up/f_down не об'єднуються в R та v.
3. Немає «guard»-інтервалів: краї рампи (розворот ГКН/VCO, перехідний процес ФАПЧ/фільтра) потрапляють у FFT і розмазують спектр.
4. DC/тренд: відлік 2048 як «нуль» — реальний зсув АЦП інший; при AC-зв'язку тренд уздовж рампи дає низькочастотний «хвіст», що маскує близькі цілі.
5. Вікна: є Hann/Hamming/Blackman, немає **Blackman-Harris (4-term, −92 дБ)** та **Kaiser (регульована β)** — саме вони потрібні, коли сильний сигнал прямого проходження (0 м) або близька ціль маскують слабкі далекі (динамічний діапазон 12-бітного АЦП ≈ 70 дБ).
6. Інтерполяція піка: парабола по **лінійних** амплітудах зміщена до ~0,1 біна для Hann; потрібна парабола по **дБ** (точна для гаусового вікна, похибка < 0,02 біна для Hann з 2× zero-pad) або оцінки Quinn/Jacobsen/Candan, які потребують **комплексного** спектра — його зараз викидають.
7. Виявлення піків: усі локальні максимуми вище частки від глобального максимуму. Без оцінки шумового рівня і без мінімальної відстані між піками таблиця заповнюється бічними пелюстками (на скріншоті 1 піки 2, 4, 5 — це пелюстки піка 1).
8. Немає усереднення між кадрами (non-coherent integration), max-hold, ні режиму «range-Doppler» для `burst > 1`.
9. Шкала не калібрована (дБ відносно «максимуму, що розпадається»), SNR не оцінюється.

### 3.4. Рекомендований конвеєр (PC-side, модуль `RadarDsp`)

```
raw uint16[N] ─▶ 1. Сегментація: chirpsInFrame M, ramp UP/DOWN, guard g % з кожного краю
             ─▶ 2. Перетворення у float, віднімання середнього (або лінійна детрендизація) по сегменту
             ─▶ 3. (опц.) Децимація ×D: half-band FIR каскад або polyphase FIR; Fs_d = Fs/D
             ─▶ 4. (опц.) ВЧ-фільтр / «range gain» (R²…R⁴ компенсація = підсилення з частотою)
             ─▶ 5. Вікно: Hann | Blackman-Harris-4 | Kaiser(β) | Flat-top; множення на 1/CG (когерентний коефіцієнт)
             ─▶ 6. Zero-pad ×Z (2…8) до степеня 2
             ─▶ 7. Real-FFT (N/2-точкова комплексна + розділення), twiddle/вікно кешовані
             ─▶ 8. Комплексний спектр ─▶ потужність ─▶ dBFS (0 дБ = повна шкала синусоїди)
             ─▶ 9. Усереднення: EMA по потужності (α), max-hold, min-hold; (burst) когерентне/Doppler-FFT
             ─▶ 10. Оцінка шуму: медіана/percentile у ковзному вікні; CFAR (CA або OS) → поріг(k)
             ─▶ 11. Піки: локальні максимуми вище CFAR, мінімальна відстань = ширина головної пелюстки,
                    інтерполяція по дБ (або Quinn-2 по комплексних бінах) → f̂, A, SNR
             ─▶ 12. Пара UP/DOWN → R, v (трикутник) або R (пилка); зсув нуля R_offset; таблиця цілей
             ─▶ 13. Трекінг між кадрами (найближчий сусід/α-β фільтр) — для стабільних ID цілей
             ─▶ 14. (опц.) Фаза біна цілі між кадрами → мікропереміщення/вібрація: ΔR = λ·Δφ/(4π)
```

Деталі за кроками:

- **1. Сегментація.** Параметри: `chirpsInFrame` (з burst), `rampShape` (трикутник/пилка/лише UP), `guardPct` (типово 5–10 %). Бажано отримувати від MCU індекс початку рампи або гарантувати фазову прив'язку старту АЦП до DAC (зараз це неявне припущення).
- **2. Детренд.** `x -= mean(x)` мінімум; краще `x -= (a + b·t)` (МНК-пряма) — прибирає нахил від AC-зв'язку та зсув АЦП.
- **3. Децимація.** Для f_b,max ≈ 0,5 МГц: D = 32 (Fs_d = 1,88 МГц), 3 стадії half-band FIR ×2 + FIR ×4; або один polyphase FIR. Користувач задає «макс. дальність», D обчислюється автоматично. Це ж дозволяє на MCU надсилати децимований потік і вирішити проблему USB (§4.6).
- **5. Вікно.** Таблиця: Hann (ENBW 1,5 біна, −31 дБ), Blackman-Harris-4 (2,0; −92 дБ), Kaiser β=9 (≈ −67 дБ, регульовано), Flat-top (3,8; точна амплітуда). Коефіцієнти CG та ENBW використати для калібрування dBFS і для перерахунку ширини головної пелюстки (крок 11).
- **7. FFT.** Зараз `std::complex<float>` radix-2 із перерахунком `cos/sin` на кожен рівень. Зробити: кеш twiddle-факторів і вікна за розміром, real-FFT трюк (×2 швидше), компіляція DSP з `/O2 /arch:AVX2 /fp:fast`. Для 65 536 точок очікувано 1–3 мс. Залишити «без залежностей»; якщо колись дозволити залежність — `pocketfft` (header-only) або `kissfft`.
- **8. Шкала.** `P_dBFS = 10·log10(|X_k|² · (2/(N·CG))²)` для синусоїди повної шкали = 0 дБ; шум на рівні 12-бітного АЦП ≈ −74 дБ − 10·log10(N/2) (processing gain) ⇒ з повною рампою шумовий поріг ≈ −120 dBFS на бін.
- **10. CFAR.** CA-CFAR: поріг `T_k = α·mean(training)`, `α = T·(P_fa^(−1/T) − 1)`; OS-CFAR (k-та порядкова статистика, k ≈ 0,75·T) стійкіший до кількох близьких цілей. Параметри: guard = 2–4 біни, training = 16–32, P_fa = 1e-3…1e-6. Для одноцільових лабораторних сценаріїв достатньо «медіана + X дБ».
- **11. Інтерполяція.** Парабола по дБ: `δ = ½·(L₋₁ − L₊₁)/(L₋₁ − 2L₀ + L₊₁)`, `f̂ = (k+δ)·Δf`. Quinn-2 / Jacobsen по комплексних бінах — без зміщення для прямокутного/Hann.
- **12. Об'єднання UP/DOWN.** Для багатьох цілей виникає проблема пар («привиди»); простий підхід — сортування за амплітудою + допуск за Доплером; показувати також «сирі» f_up/f_down.
- **9/burst.** При M чірпів у кадрі: матриця M×N_bins комплексних range-FFT → Hann по повільному часу → FFT по M → range-Doppler карта; MTI = віднімання середнього по M (прибирає нерухомий клаттер). Обмеження пристрою: при T_PRI = 2,18 мс однозначна швидкість ±1,4 м/с на 24 ГГц — для автомобілів замало, для людей/вібрацій достатньо; варто показувати ці межі в UI.
- **14. Фаза.** Для вібраційних/дихальних вимірювань: зафіксувати бін цілі, брати `arg(X_k)` щокадру, розгортати фазу; 1° на 24 ГГц = 17 мкм.

### 3.5. Що саме виводити користувачу

- **Range profile**: дБ ↔ дальність (м) зверху та частота (кГц) знизу; UP і DOWN накладені різним кольором; усереднена/max-hold траса; лінія CFAR-порогу; маркери піків з підписами «R / v / SNR».
- **Таблиця цілей**: №, f_up, f_down, R (м), v (м/с), A (dBFS), SNR (дБ), ширина піка (біни) — з сортуванням і копіюванням у буфер.
- **Водоспад (range–time)**: вісь дальності, вісь часу (с або № кадру), колірна шкала в дБ з фіксованим діапазоном, палітри viridis/inferno/turbo (Jet залишити як опцію).
- **Range-Doppler** (при burst > 1): теплова карта + маркер максимуму.
- **Осцилограма IF**: вісь часу (мс/мкс) і положення рамп (UP/DOWN/guard) кольоровим фоном; курсори Δt, Δv, 1/Δt.
- **Параметри радара** у панелі: f₀, B, T_ramp (обчислювати з chirp freq або вводити), форма модуляції, напрямок, R_offset, λ.

### 3.6. Приклад обчислення R і v (псевдокод)

```cpp
struct RadarParams { double f0Hz, bandwidthHz, rampSec, rangeOffsetM; bool triangle; };

inline double RangeFromBeat(double fb, const RadarParams& p) {
    return 299792458.0 * p.rampSec * fb / (2.0 * p.bandwidthHz) - p.rangeOffsetM;
}
inline void RangeVelocityFromPair(double fUp, double fDn, const RadarParams& p,
                                  double& R, double& v) {
    const double c = 299792458.0, lambda = c / p.f0Hz;
    R = c * p.rampSec * (fUp + fDn) / (4.0 * p.bandwidthHz) - p.rangeOffsetM;
    v = lambda * (fDn - fUp) / 4.0;          // >0: наближення
}
// Інтерполяція піка по дБ
inline double PeakOffsetDb(float lm1, float l0, float lp1) {
    double d = lm1 - 2.0 * l0 + lp1;
    return (std::fabs(d) < 1e-12) ? 0.0 : 0.5 * (lm1 - lp1) / d;
}
```

## 4. Пропозиції щодо функціональності

### 4.1. Вимірювання та DSP (пріоритет 1)
- Модуль `RadarDsp` (§3.4) з юніт-тестами на синтетичних сигналах (тон + шум, дві цілі, доплер).
- Панель «Processing»: сегментація, guard, децимація, вікно, zero-pad, усереднення, CFAR, інтерполяція.
- Панель «Radar»: f₀, B, T_ramp, форма модуляції, R_offset — з обчисленням і показом ΔR, R_max, Δv, v_max.
- Абсолютна шкала dBFS, калібрування вольт/коди, калібрувальна Fs у налаштуваннях.
- Таблиця цілей + трекінг + експорт.

### 4.2. Запис і відтворення (пріоритет 1)
- Бінарний файл сесії `.facq`: заголовок файлу (версія, Fs, параметри) + послідовність кадрів (`FrameHeader` + дані) + індекс у кінці; запис «на льоту» з COM-потоку.
- Режим **Replay**: відкрити файл замість порту, скраббер по кадрах, швидкість ×0,25…×8, крок кадру ←/→. Це дає відтворювані тести DSP і розробку UI без заліза.
- Експорт: CSV усього кадру (є), CSV таблиці цілей за сесію, WAV (IF-сигнал, 16-біт, Fs_d) для аналізу в Audacity/MATLAB, `.npy`/бінарний dump, PNG знімок графіка.

### 4.3. Взаємодія (пріоритет 2)
- **Live / Hold**: зараз будь-який новий кадр перекриває вибраний у списку. Кнопка «Hold» (пауза відображення, буфер продовжує накопичуватись) + «Live».
- Курсори/маркери на всіх графіках: одиночний, дельта, прив'язка до піка; readout у правому верхньому куті.
- Зум колесом **навколо курсора**, протягування для панорамування, рамка для зуму, подвійний клік — автомасштаб; синхронний зум UP/DOWN.
- Гарячі клавіші: Space (Start/Stop), T (Trigger), H (Hold), R (Record), ←/→ кадри, Ctrl+S (Save), F11.
- Автопідключення до пристрою за VID/PID при старті; автоматичний `GET_STATUS` після з'єднання; індикатор стану в статус-барі (зелений/сірий).
- Збереження налаштувань (реєстр/INI/JSON поруч із `.exe`) і наборів пресетів («24 GHz lab», «6 MHz test tone»).

### 4.4. Діагностика з'єднання (пріоритет 2)
- Статус-бар: fps кадрів, МБ/с, втрачені кадри (за розривами `frame_id`), CRC-помилки, заповненість буфера, затримка (ts_MCU vs rx_tick).
- Журнал: віртуальний список з фільтрами TX/RX/ACK/STATUS, кнопка «Copy», експорт у файл; рядки на кожен кадр лише у verbose.

### 4.5. Якість коду (пріоритет 2)
- `std::shared_ptr<const ChirpFrame>` замість копій; монотонний `seq`.
- DSP у робочому потоці; UI отримує `RampResult` (спектри в дБ, піки, R/v); коалесування.
- Прибрати мертвий код або завершити тему; усі ID в `resource.h`; `struct AcqSettings`/`DspSettings` як модель.
- Табличний інкрементальний CRC32; `ResetStream()` без скидання статистики.
- Тестовий проєкт (консольний, без залежностей): парсер на фрагментованому/зашумленому потоці, CRC, FFT проти прямого DFT, інтерполяція піка, R/v.
- CI: GitHub Actions з `windows-latest` + MSBuild (збірка Release x64 і запуск тестів).

### 4.6. Пропозиції до прошивки (тісно пов'язані з PC-боком)
- **12-бітне пакування** відліків (3 байти на 2 відліки): −25 % трафіку без втрат.
- **Децимація/вибір смуги на MCU** (CIC + FIR, STM32H7 має FMAC/CMSIS-DSP): при D = 16 трафік падає в 16 разів, і кадри підуть на 30+ fps по USB FS.
- Або **USB HS** (H743 має HS-ядро, потрібен ULPI PHY) — до 30–40 МБ/с.
- У заголовку кадру: `chirps_in_frame`, `ramp_start_index`, `guard_samples`, `dac_ramp_shape`, часова мітка в мкс; FFT від MCU — комплексна або з явним числом бінів.
- Попередня корекція нелінійності VCO таблицею DAC (pre-distortion) — покращує ширину піка більше за будь-яку обробку на ПК.

## 5. Редизайн UI/UX

### 5.1. Проблеми поточного інтерфейсу (за кодом і скріншотами)
- Чотири вкладки ховають одна одну: не можна одночасно бачити осцилограму й спектр; налаштування обробки (FFT/вікно) — у підвалі другої вкладки, налаштування MCU — на окремій вкладці з 80 % порожнього простору.
- Список кадрів зліва займає 240 px, але несе мало інформації (ID, t, «Peak» обрізаний).
- Графіки без осей часу (осцилограма) та без осей/шкали (водоспад); без курсорів; текст −9 px (нечитабельно на HiDPI).
- Jet-палітра: перцептивно нерівномірна, погана для дальтоніків; на світлому тлі водоспад виглядає чужорідно.
- Кнопки H−/H+/V−/V+ дублюють колесо миші і займають місце; статус-бар — один довгий рядок.
- Немає індикації «що зараз робить пристрій» (режим/захоплення) крім тексту у статус-барі після Get Status.

### 5.2. Принципи
1. Головний екран — для **радарного вимірювання**: range profile + водоспад + таблиця цілей видимі одночасно; осцилограма — поруч або в другому «перспективному» вигляді.
2. Усе, що впливає на результат (вікно, guard, CFAR, параметри радара), — у бічній панелі з миттєвим застосуванням (без «Apply»), з підказками і видимими похідними величинами (ΔR, R_max).
3. Одна візуальна система: сітка 8 px, шрифт Segoe UI 9–10 pt із масштабуванням за DPI, світла і темна теми (у `Theme.h` палітра вже є — її варто довести до кінця).
4. Дані завжди підписані: одиниці на кожній осі, колірна шкала біля водоспаду, легенда UP/DOWN/avg.

- **Рендеринг графіків**: лишити GDI з DIB-буфером (достатньо для 60 fps при ~1 М точок з min/max-децимацією), або перейти на **Direct2D + DirectWrite** (входять до Windows SDK): антиаліасинг, швидкий полілайн, коректний текст на HiDPI. Обгортка `IPlotRenderer` дозволить змінити бекенд пізніше.

- **Тема**: довести `Theme.h` до пари палітр (light/dark), застосувати до всіх `Render()`; системну тему визначати через реєстр `AppsUseLightTheme`.
- Палітри: viridis / inferno / turbo таблицями 256 кольорів у `ColorMap` (як Jet зараз).

### 6.5. Що запозичити у першу чергу

1. **Дві осі (м + кГц) і dBFS** — стандарт для всіх радарних GUI (TI, Infineon, SiRad, ckflight).
2. **Таблиця цілей із SNR** (uRAD, SiRad, WaveForms «Components») замість списку кадрів як головної лівої панелі.
3. **Режими трас** Clear/Avg/Max-hold/Persistence (Keysight, WaveForms, PicoScope) — дешево реалізувати, сильно підвищує читабельність слабких цілей.
4. **Запис/відтворення raw** (Infineon, Acconeer HDF5, TI DCA1000) — найкраща інвестиція для розробки DSP без заліза.
5. **Водоспад як RTI** (MIT: 80 дБ вікно, viridis/turbo з Gqrx, readout часу під курсором).
6. **Показ проміжних стадій обробки** (matthuszagh/fmcw) — перемикач «що малюємо: raw / після детренду / після вікна / спектр» для налагодження.
7. **Докінг + пресети + темна тема** (Spike, Friture, Saleae) — через MFC Feature Pack без сторонніх залежностей.
8. **Калькулятор похідних величин** (Acconeer resource calculator, SiRad): ΔR, R_max, Δv, v_max, навантаження на USB — показувати одразу при зміні параметрів.

## Додаток B. Швидка перевірка гіпотез на наявних даних
- Подати тестовий тон 6 МГц (як на скріншотах) і порівняти f̂ при FFT 16 k vs повна рампа — очікувана похибка/розкид зменшиться пропорційно до √(T_obs).
- Два тони на відстані 2 кГц (менше за поточний бін 3,67 кГц): зараз нерозрізнювані, з повною рампою (916 Гц/бін) — розрізняються.
- Імітувати слабку ціль на −50 дБ поруч із сильною: з Hann бічні пелюстки її «з'їдять», з Blackman-Harris — ні.
